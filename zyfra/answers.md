# JS

1. `var`: функциональная или глобальная; `let` и `const`: блочная область видимости. `const` — неизменяемость ссылки.
2. Замыкание — это функция, запоминающая переменные из своей лексической области видимости, имеющая доступ к ним даже после выполнения внешней функции.
3. Стрелочная функция не имеет своего `this`, `arguments`, не может использоваться как конструктор и не имеет `prototype`.
4. Call Stack («стек вызовов») выполняет вызовы функций один за другим (синхронно). Event Loop («цикл событий») следит за очередью задач (макро- и микрозадач) и добавляет их в Call Stack при его освобождении.
5. Микрозадачи (`Promise.then`, `queueMicrotask`) выполняются сразу после текущей задачи до следующей макрозадачи. Макрозадачи (`setTimeout`, события, `setInterval`) запускаются после выполнения очереди микрозадач.
6. Прототипное наследование — это механизм, при котором объекты наследуют свойства и методы от других объектов через ссылку на их прототипы.
7. `Spread` (`...`) — «разворачивает» массив и объект в отдельные элементы. `Rest` (`...`) — собирает остальные элементы функции или массива в один массив.
8. Функция, результат которой зависит только от входных параметров, не имеющая побочных эффектов.
9. Используя объект `AbortController`. Для `Observable` пайп `takeUntil()`
10. JSON-методы: `JSON.parse(JSON.stringify(obj))`. Рекурсивный `Spread`.
11. **Делегирование событий** — это техника обработки событий в JavaScript, при которой мы назначаем обработчик события **родительскому элементу**, чтобы отлавливать события от его потомков. Это достигается за счёт механизма **всплытия событий (event bubbling)**, который позволяет событиям перемещаться вверх по дереву DOM от целевого элемента (`target`) к его родителям.
- **Уменьшение количества обработчиков.**
  - Вместо добавления обработчика к каждому дочернему элементу добавляется только один на общего родителя.
- **Динамическая обработка.**
  - Работает и с элементами, которые были добавлены в DOM динамически (например, сгенерированы JavaScript после загрузки страницы).
- **Улучшение производительности.**
  - Сокращается количество обработчиков в памяти, особенно если нужно обрабатывать много похожих элементов.
- **Удобство в управлении.**
  - Все события для схожих элементов централизованы в одном месте, упрощая логику приложения.
12. Reflow — это процесс, когда браузер повторно вычисляет положение и размеры элементов на странице. Repaint — это процесс перерисовки внешнего вида элементов на экране.

| **Параметр** | **Reflow** | **Repaint** |
| --- | --- | --- |
| **Что выполняется** | Пересчёт геометрии (размеров, позиции) элементов | Перерисовка стилей |
| **Когда вызывается** | Изменения размеров, положения, структуры DOM или метрики элементов | Изменения внешнего вида |
| **Что затрагивает** | Затрагивает всё дерево рендеринга от элемента до родителя/дочерних | Затрагивает только стили |
| **Стоимость для CPU** | Тяжёлый процесс, дорогой для производительности | Легче по сравнению с reflow |

 **Изменения вне документа (в памяти):**
  - Используйте **`DocumentFragment`** для работы с целыми частями DOM.
  - Сначала изменяйте элемент в памяти, а после добавляйте его в DOM.

 **Сводите к минимуму изменения стилей:**
  - Объединяйте изменения стилей: вместо нескольких установок измените только одно свойство стилей.

 **Избегайте лишнего чтения DOM:**
  - Методы, такие как `offsetHeight`, `getBoundingClientRect()`, вынуждают браузер синхронизировать DOM и CSSOM перед выполнением (это вызывает reflow).
  - Старайтесь кешировать результаты этих методов.

 **Используйте свойства, которые не вызывают reflow:**
  - Например, изменение `opacity` вызывает только repaint, а не reflow.
  - Анимации на свойствах, которые не требуют перекомпоновки (`transform`, `opacity`), будут работать быстрее.

 **Используйте классы для изменения стилей:**
  - Вместо непосредственного изменения нескольких стилей одного элемента переключайте классы. Это может уменьшить количество reflow/repaint.

 **Работайте с DOM-командами разом:**
  - Избегайте частого добавления/удаления элементов из DOM по одному. Используйте методы, такие как:
    - `innerHTML` (но только для доверенного контента).
    - Создание элементов через `DocumentFragment`.

 **Скрывайте элементы перед большими изменениями:**
  - Скройте элемент (`display: none`), выполните изменения, затем снова отобразите.

 **Оптимизируйте сложные анимации:**
  - Используйте `requestAnimationFrame` для более плавной работы различных DOM-изменений.

# CSS

1. Для небольших проектов с минимальными усилиями подойдет **обычный подход** или **BEM**.
Если требуется оставаться организованным в крупных проектах, то лучше выбрать **SMACSS**, **ITCSS** или **Atomic CSS**.
**OOCSS** и **BEM** помогают создавать модули, которые удобно повторно использовать.
2. Каскадирование помогает браузеру установить приоритет между несколькими конфликтующими правилами.
Каскадирование использует комбинацию:
  - Специфичности (ID > Классы > Теги).
  - Порядка правил.
  - Источников правил.
  - `!important`, который перебивает всё.
**Понимание специфичности и каскадирования важно для написания неизбыточного и предсказуемого CSS.**
3. Для вставки декоративных элементов, иконок, стрелок, подсказок, создания псевдоэлементов без добавления реального DOM-контента.
4. Как обрезать текст через стили?
- overflow: hidden;
- text-overflow: ellipsis;
- white-space: nowrap;

5. Инструменты типа DevTools, Lighthouse и Puppeteer помогают выявить проблемные места, связанные с **Reflow** и **Repaint**, а использование рекомендаций и стратегий оптимизации позволяет ускорить рендеринг страницы и улучшить производительность вашего веб-приложения.
6. Для современных проектов лучше использовать **Flexbox** (для одномерных макетов) или **Grid Layout** (для сеточных структур).

| **Метод** | **Сценарий использования** | **Преимущества** | **Недостатки** |
| --- | --- | --- | --- |
| **Flexbox** | Для выравнивания элементов в одной строке или столбце, простое распределение пространства между элементами | Простота, гибкость, адаптивность | Только одномерное выравнивание |
| **Grid** | Сложные сеточные раскладки или организации строк/столбцов | Полный контроль, мощь двухмерного выравнивания | Сложность в изучении |
| **Position** | Точное позиционирование элементов | Полный контроль над координатами | Требует дополнительных настроек для адаптивности |
| **Таблица (table)** | Вертикальное выравнивание | Простота в базовых задачах | Не подходит для сложных макетов, устаревший метод |
| **Флоаты** | Для потокового размещения содержимого | Универсальная поддержка | Устаревший подход |
| **CSS Frameworks** | Быстрое позиционирование и выравнивание с помощью готовых CSS-классов | Быстрое внедрение | Накладные стили, мало контроля |

7. Какие есть востребованные фичи в css-препроцессорах?
- Вложенность (Nested CSS)
- Переменные и миксины
- Наследование и расширения (`extend`)
- Функции и математические операции
- Импорты и модульность


# Angular

1. `ngOnChanges`, `ngOnInit`, `ngDoCheck`, `ngAfterContentInit`, `ngAfterContentChecked`, `ngAfterViewInit`, `ngAfterViewChecked`, `ngOnDestroy`.
2. Angular использует древовидную архитектуру Change Detection для проверки и применения изменений состояния компонентов. По умолчанию запускается автоматически при асинхронных событиях и вводе пользователя.
- `Default`: проверяет всегда.
- `OnPush`: проверка только при изменении входных ссылок (`@Input`) или явном ручном запуске.
- Ручная инициация: метод `detectChanges()` или `markForCheck()` из сервиса `ChangeDetectorRef`.
3. `zone.js` играет ключевую роль в Angular, поскольку он обеспечивает механизмы для автоматического определения изменений в веб-приложении и их последующего отражения в пользовательском интерфейсе.
- Обертка над асинхронными операциями
- Запуск Change Detection
4. Dependency Injection в Angular обеспечивает простой, удобный и эффективный механизм управления зависимостями. Это позволяет писать более модульный, тестируемый и поддерживаемый код. DI минимизирует плотное связывание компонентов между собой, что делает приложение гибким для масштабирования и изменения.
5. Оба подхода для работы с формами в Angular имеют свои преимущества и подходят для разных сценариев. Если вам нужна легкость и простота — используйте **template-driven формы**. Если требуется сложная, полноценная настройка с высокой управляемостью и структурой кода — выбирайте **reactive формы**.

| **Критерий** | **Template-driven** | **Reactive** |
| --- | --- | --- |
| **Управление формой** | Управляется из HTML-шаблона | Управляется из TypeScript-кода |
| **Валидация** | Использует встроенные валидаторы или директивы | Использует функции и классы Angular |
| **Контроль состояния** | Ограниченный контроль | Полное управление |
| **Сложность** | Подходит для простых форм | Подходит для сложных и динамических |
| **Тестирование** | Более сложное | Простое тестирование логики формы |

6.  Функции для преобразования отображаемых данных в шаблонах (например, форматирование даты и чисел).
- Pure: кешируются и вызываются только при изменении входных параметров.
- Impure: вызываются на каждом цикле обнаружения изменений (даже если параметры не изменились).
7. RxJS — это фундаментальная библиотека для работы с потоками данных в Angular. Она упрощает управление асинхронным кодом и событиями.
- Понимание **холодных** и **горячих потоков** критично для правильной работы с RxJS, т.к. это определяет, как будут обрабатываться данные (независимо или совместно для подписчиков).
- Без RxJS такие вещи, как взаимодействие с формами, событиями или HTTP-запросами, были бы значительно сложнее.
8. NgRx — это библиотека управления состоянием, созданная для Angular и основанная на архитектурном паттерне Redux/Flux, с использованием однонаправленного потока данных. NgRx обеспечивает централизованное хранилище состояния (**Store**) и строгую структуру для управления состоянием.
   Angular сервисы — это базовый инструмент Angular для организации общего состояния и логики в приложении. Они позволяют разделять бизнес-логику и использовать данные через Dependency Injection (DI). В связке с **RxJS**, сервисы могут обрабатывать асинхронные операции, получать данные из API и управлять состоянием

| **Параметр** | **Angular Services** | **NgRx** |
| --- | --- | --- |
| **Сложность** | Низкая | Высокая |
| **Boilerplate-код** | Минимальный | Много кода |
| **Централизованность** | Отсутствует (множество сервисов) | Централизованное хранилище |
| **Отладка** | Средняя (инструменты отсутствуют) | Redux DevTools |
| **Масштабируемость** | Средняя | Высокая |
| **Асинхронность** | RxJS, ручное управление | Встроенные механизмы (Effects) |
| **Предсказуемость** | Зависит от реализации | Однозначная благодаря архитектуре |
| **Производительность** | Лучшая при малых объемах состояния | Хорошая при правильной настройке |

- Если проект **небольшой или средней сложности**, начните с **Angular Services**.
- Если приложение **большое, сложное или многостраничное**, с высокой степенью взаимодействия данных — **NgRx** будет предпочтительнее.

9. Signals: новая реактивная примитивность для оптимизации и упрощения Change Detection.
Standalone компоненты: компоненты без обязательного объявления в модулях (NgModules).
Новый синтаксис шаблонов: упрощенная запись структурных директив (*defer, @if, @for), упрощение использования директив и повышения читаемости.

# Web

1. «модуль», «наблюдатель» (Observer), «одиночка» (Singleton), «фабрика» (Factory), «стратегия» (Strategy), «декоратор» (Decorator), MVC/MVVM
2. DRY (Don't Repeat Yourself) Не дублируйте код.
KISS (Keep It Simple, Stupid) Стремитесь к простоте.
YAGNI (You Aren't Gonna Need It) Не добавляйте функциональность, которая "может понадобиться в будущем"
- Single Responsibility Principle (Принцип единственной ответственности): один объект, класс или функция должны быть ответственны только за одну задачу.
- Open/Closed Principle: сущности должны быть открыты для расширения, но закрыты для модификации.
- Liskov Substitution Principle: подклассы должны быть взаимозаменяемы с суперклассами.
- Interface Segregation Principle: поддерживайте маленькие и конкретные интерфейсы.
- Dependency Inversion Principle: модули верхнего уровня не должны зависеть от модулей нижнего уровня.
- Immutability Избегайте мутаций
8. Микро-фронтенды — это архитектурный подход, который переносит концепцию микро-сервисов на фронтенд приложения. Вместо разработки и сборки монолитного фронтенда, приложение разбивается на несколько независимых модулей
**Single SPA (Single Simple Page Application)** — это библиотека, которая позволяет разработчикам комбинировать несколько микрофронтендов в одном приложении.
**Преимущества**:
- Независимость разработки.
- Значительное упрощение масштабирования.
- Возможность использования нескольких технологий в проекте.
**Недостатки**:
- Усложнение начальной настройки.
- Повышенные требования к координации команд.
- Дополнительная нагрузка на инфраструктуру (например, разбиение CSS и JS).
- Потенциальные проблемы с производительностью (множество бандлов).
